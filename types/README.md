# PCLib - Process Control DDT Library for EcoStruxure Control Expert

Version 1.00. 27 Derived Data Types for common process-industry equipment, built for HMI faceplates and aligned with ISA-88, ISA-18.2, ISA-101, NAMUR NE107 and the other standards listed below.

Generated by `gen_pclib.py`. Edit the definitions there and re-run; do not hand-edit the .xdd files.

## Files

| File | Purpose |
|---|---|
| `xdd/PCLib_All.xdd` | Every DDT in dependency order. **Import this one.** |
| `xdd/<Type>.xdd` | One DDT per file. Import its dependencies first (listed below). |
| `PCLib_Members.csv` | Flat member list with ISA-88 role and MTP mapping |
| `gen_pclib.py` | Source of truth / generator |

## Importing into Control Expert

1. Open the project. In the Project Browser, right-click **Derived Data Types** and choose **Import...**
2. Select `xdd/PCLib_All.xdd`. If a type already exists, choose whether to keep or replace it.
3. Run **Build > Analyze Project** to check the types.
4. Declare instances in the Data Editor, e.g. `P101 : T_Motor;`, `FT101 : T_AI;`.

The `.xdd` files leave out the checksum attributes; Control Expert works them out on import. If your version rejects the file header, export any DDT from your project and copy its `<fileHeader>` line into the generator.

Totals use `LREAL`. If your CPU or firmware does not support LREAL, regenerate with `python gen_pclib.py --no-lreal`.

### Control Expert Classic V16.2

1. Import `export/PCLib_CE_V16.2.xdd` as described above, then **Analyze Project**.
2. Declare one instance per piece of equipment (e.g. `P101 : T_Motor`).
3. For Ignition (or any OPC UA client) to read the instances by name, enable symbolic access:
   **Tools > Project Settings > PLC embedded data > Data dictionary**, then rebuild and download.
   Instances must be unlocated variables.

### Ignition 8.1 Perspective

The JSON holds 26 UDT definitions in a `PCLib` folder, matching the DDTs member for member.
Nested DDTs (`Mode`, `Alm_*`, `Run`, `Drv`...) are nested UDT instances. Arrays are folders with one tag per element.

1. In the Designer Tag Browser, select **Data Types**, click **Import Tags** (or right-click > Import Tags) and
   choose `export/PCLib_Ignition81.json`.
2. Create an OPC UA connection to the PLC (Gateway > Config > OPC Client > OPC Connections). Use the M580
   embedded OPC UA server, a BMENUA0100 module, or EcoStruxure OPC UA Server Expert.
3. Create an instance of a UDT under **Tags** (e.g. `P101` of type `PCLib/T_Motor`) and set its parameters:

| Parameter | Meaning | Example |
|---|---|---|
| `OPCServer` | Ignition OPC connection name | `M580_Line1` |
| `PathPrefix` | Node-ID prefix used by your OPC server | `ns=2;s=` (check with the OPC Quick Client) |
| `BaseTag` | PLC instance name | `P101` |

   Each tag's OPC path is `{PathPrefix}{BaseTag}.<Member>`. Browse one variable in the OPC Quick Client
   first and copy its prefix, because the namespace index and path syntax differ between Schneider OPC servers.
4. In Perspective, bind faceplates to the instance (e.g. `[default]P101/Sts_State`). `Cfg_`, `Cmd_`, `Sim_`
   and `Prm_` tags are writable; everything else is read-only (ISA-101: the HMI never writes PLC status).

**Alarms:** each `T_Alarm` / `T_AlmLim` UDT has an Ignition alarm on `Sts_Active`, so PLC alarms appear in the
Perspective Alarm Status Table and alarm journal. The alarm is enabled by `Cfg_En`, and its priority comes from
`Cfg_Priority` (1=Critical 2=High 3=Medium 4=Low). Acknowledging in Ignition runs a tag event script that writes
`Cmd_Ack` to the PLC, so the PLC alarm state (ISA-18.2) stays authoritative. Shelving is done in the PLC through
`Cmd_Shelve`; Ignition's own shelving only hides the alarm in Ignition.


## Standards alignment

The standards define models, behaviour and terminology. Apart from MTP, they do not prescribe PLC data layouts. PCLib carries the data each model needs, so the DFBs you write can implement the behaviour. Alignment is by design; it is not a third-party certification. Values such as alarm priorities, limits and equipment states come from your own alarm philosophy, HMI philosophy and rationalisation.

| Standard | Scope | How PCLib applies it |
|---|---|---|
| ISA-88.00.01 / IEC 61512-1 | Batch control: physical and procedural models, modes, states | Every type has an ISA-88 role (control module, equipment module, unit, phase). `Prog_` members are commands from the owning phase or equipment module. `T_Mode` adds arbitration (acquire / release / owner ID). `T_Phase` uses the Part 1 example state model (12 states) and commands (Start, Stop, Hold, Restart, Abort, Reset, Pause, Resume), with Automatic / Semi-automatic / Manual modes, recipe parameters and reports. `T_Unit` holds allocation, batch identity and equipment state (clean, dirty, in use...). |
| ISA-18.2 / IEC 62682 | Alarm management | `T_Alarm` uses the standard's state model (A Normal to H Out-of-service), including latching, time-limited shelving, suppressed-by-design and out-of-service. Chattering control (deadband, on/off delay), priority and class come from rationalisation. Events that need no operator action are status bits, not alarms (e.g. pump changeover). |
| ISA-101.01 | HMI design | Modes, states and NE107 status are integers, so graphics can use consistent symbols without colour logic in the PLC. `Sts_CmdMask` lets the HMI grey out invalid phase commands. Tag and description are in the type for faceplates. |
| ISA-5.1 | Instrument identification | `Cfg_Tag` holds the ISA-5.1 tag (e.g. FT-101). Limit alarms follow HH / H / L / LL naming. |
| NAMUR NE107 | Field device diagnostics | `Sts_NE107` on every field-device control module (Good / F / C / S / M). `Inp_NE107` takes the status from HART or fieldbus devices. |
| NAMUR NE43 | 4-20 mA failure signal levels | `T_AI` bad-signal limits default to NE43 (below 3.6 mA, above 21 mA). `T_GasDet` fault and over-range thresholds are configurable. |
| VDI/VDE/NAMUR 2658-4 (MTP) | Module Type Package data objects for modular plants | Each type lists its nearest MTP data assembly (AnaMon, BinMon, MonBinVlv, MonAnaVlv, MonBinDrv, MonAnaDrv, PIDCtrl, LockView16). Mode values map to MTP Offline / Operator / Automatic. Member names are not MTP attribute names, so an MTP export needs a mapping layer. |
| ISA-84 / IEC 61511 | Safety instrumented systems | `T_Intlk` and `T_ESD` follow the bypass-management requirements (authorisation, time limit, indication, logging data), first-out, manual reset after trip and de-energise-to-trip. They are **basic process control (BPCS) functions only**, not SIFs. |
| IEC 61131-3 | PLC languages and data types | Elementary IEC data types only. Identifiers are checked against the 32-character limit and IEC / Control Expert reserved words. |
| ISA-95 / IEC 62264 | Enterprise-control integration | Level 1-2 data. `T_Unit` and `T_Phase` expose batch ID, recipe, product and reports for MES collection. |

### ISA-88 physical and procedural model

| ISA-88 level | PCLib types |
|---|---|
| Support | `T_Alarm`, `T_AlmLim`, `T_Mode`, `T_RunTime`, `T_Intlk`, `T_ESD` |
| Control module | `T_AI`, `T_DI`, `T_DValve`, `T_CValve`, `T_Motor`, `T_VFD`, `T_Heater`, `T_PID`, `T_PumpProt`, `T_Totalizer`, `T_HeatEx`, `T_Analyzer`, `T_GasDet` |
| Equipment module | `T_PumpDS`, `T_Agitator`, `T_Compressor`, `T_Conveyor`, `T_DosePump` |
| Equipment module / Unit vessel | `T_Tank` |
| Equipment phase | `T_Phase` |
| Unit | `T_Unit` |

Control modules take `Prog_` commands only from the owner that has acquired them through `Mode.Prog_Acquire` (ISA-88 arbitration). Out-of-service and Maintenance modes are site extensions; ISA-88 itself defines Automatic, Semi-automatic and Manual.

### Alarm state model (ISA-18.2 / IEC 62682)

`Sts_State`: 0=A Normal 1=B Unack 2=C Acked 3=D RTN-Unack 4=E Latched 5=F Shelved 6=G Suppressed-by-design 7=H Out-of-service

### Phase state model (ISA-88 Part 1)

`Sts_State`: 0=Idle 1=Running 2=Complete 3=Pausing 4=Paused 5=Holding 6=Held 7=Restarting 8=Stopping 9=Stopped 10=Aborting 11=Aborted  
Commands (`Prog_Cmd`, `Sts_CmdMask` bit n): 1=Start 2=Stop 3=Hold 4=Restart 5=Abort 6=Reset 7=Pause 8=Resume

MTP services use a PackML-derived state model (Execute, Completing, Unholding...). If a phase is exposed as an MTP service, map Running to Execute, Complete to Completed, and so on.

### Equipment state (ISA-88)

`Sts_EqState` on `T_Unit` and `T_Tank`: 0=Available-clean 1=In use 2=Dirty 3=Cleaning (CIP) 4=Sterilising (SIP) 5=Maintenance 6=Out of service

## Conventions

| Prefix | Meaning | Written by |
|---|---|---|
| `Inp_` | Field / upstream input | I/O mapping or upstream logic |
| `Cfg_` | Configuration / tuning | Engineer (HMI with access control) |
| `Cmd_` | Operator command. Booleans are **one-shot**: the logic clears them after acting | HMI |
| `Prog_` | Command from the ISA-88 owner (phase, equipment module, batch server) | Owner logic |
| `Prm_` / `Rpt_` | ISA-88 recipe parameters / report values | Batch server / phase logic |
| `Out_` | Output to field or downstream logic | Equipment logic |
| `Sts_` | Status | Equipment logic |
| `Val_` | Calculated value | Equipment logic |
| `Alm_` | Alarm (T_Alarm / T_AlmLim) | Equipment logic sets `Inp_Cond` |
| `Sim_` | Simulation | Engineer |

- Booleans ending in `OK` are **TRUE = healthy**, so a broken wire or lost signal reads as unhealthy. Other `Inp_` booleans are TRUE when the condition is present.
- Interlocks (`Inp_IntlkOK`) stop running equipment. Permissives (`Inp_PermOK`) only block a start.
- `Sts_State` / `Sts_Mode` / `Sts_NE107` integers are for HMI animation. The values are listed in each member comment.
- These are **data types only**. Pair each one with a DFB (or ST section) holding the behaviour. Most types are laid out so a DFB can take the whole DDT as one IN_OUT parameter.

> **Safety:** `T_ESD`, `T_Intlk` and `T_GasDet` are for the basic process control layer and HMI. Safety Instrumented Functions with a SIL target must run in a certified safety controller (e.g. M580 Safety, SAFE task) and follow IEC 61511.
